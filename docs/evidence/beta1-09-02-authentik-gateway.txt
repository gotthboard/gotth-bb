Results
-------

- The raw Authentik token is absent from Board. Board can reach only the closed
  HTTP/1.1-over-Unix gateway surface. The gateway accepts only the Board UID,
  eight concurrent calls, fixed request/response bounds, fixed Host, fixed
  issuer origin, three pinned groups, three pinned flows, UUID-filtered user
  lookup, the bounded pending page, and flow-bound invitation
  create/list/retrieve/delete. It has no TCP listener or generic proxy.
- The real Authentik matrix positively exercised the exact user UUID filter,
  pending-group filter, exact group reads and add/remove actions, pinned-flow
  invitation create/list/retrieve/delete, creator-only visibility, and all
  forbidden administrative operations.
- Authentik 2026.5.2 has two documented raw-token excesses. Required
  `view_invitation` also permits arbitrary-recipient `send_email`, while
  removing view makes list/retrieve/delete unusable. Any authenticated
  non-superuser can also create, retrieve, use, change, and delete its own API
  tokens without explicit token model permission. The gateway implements no
  email or token operation, so Board cannot exercise either excess.
- Authentik leaves generic invitation object permissions and managed-role token
  permissions behind after target deletion. Permission-matrix cleanup removes
  only its own fixtures. Authoritative bootstrap rejects live foreign targets
  and unexpected live or expired service tokens, removes only stale
  control-role invitation tombstones, and removes only a detached,
  principal-free service managed role after proving no replacement token
  exists. Group and unrelated RBAC state remain untouched.
- Token/object files use descriptor-safe `openat2`, regular-file and
  immutability checks, strict framing, size bounds, and owned token-byte
  clearing. The outbound client uses system TLS, a fixed issuer-derived origin,
  no redirects, two-second total timeout, concrete operations, and bounded
  responses. Neither raw token nor remote error bodies are logged or retained.
- The deterministic blueprint creates the three guarded registration flows,
  accepted/pending/suspended groups, service account, exact role/model/group
  permissions, creator-scoped invitation permissions, and fixed control-object
  descriptor. Direct flow guards use the exact persisted registration-mode
  names and fail closed on Board denial or failure.

Rejected intermediate work
--------------------------

- Authentik's invitation `send_email` action has no independent permission.
  Pretending it was denied was false; this forced the owner-approved isolated
  gateway correction before implementation continued.
- An empty token-create request returned validation `400` before permission
  evaluation and hid Authentik's non-superuser self-token rule. A valid request
  proved the complete usable self-token lifecycle and the contract was
  corrected instead of preserving a fake denial.
- Repeated invitation tests exposed non-cascading guardian permission rows.
  Treating every extra row alike would have silently erased active foreign
  authority. The final mechanism deletes only absent-target tombstones and
  blocks permissions whose foreign target still exists.
- Authentik's default token manager hides expired rows. The first exact-token
  check was therefore incomplete; the final check uses `including_expired()`
  and a real expired-token fixture.
- Compose keeps the control token mounted in the Authentik server container for
  operator-invoked bootstrap. Earlier subprocess-only wording was false and was
  replaced with the exact container-lifetime boundary.
- The release contract still said three binaries after the gateway became the
  fourth. Package comments and operations documentation now match the archive.
